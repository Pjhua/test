# 智慧生活项目 —— 调试记录与改动总结

> 项目：STM32F407 + FreeRTOS + LVGL 智能家居（语音控制 / 音乐播放 / WiFi-MQTT / 传感器）
> 记录范围：语音链路稳定性排查、音乐播放器、界面状态同步、诊断体系建设

---

## 一、系统架构（相关部分）

| 模块 | 说明 |
|---|---|
| 语音识别 | HLK-V20 模块，UART3（PD9=TXD 只收不发），帧格式 `4F 00 XX F4`，唤醒帧 `AA`/`AB` |
| 音乐播放 | SD 卡(FatFs/SPI1) WAV + WM8978/I2S2 双缓冲 DMA，常驻 MUSIC 任务（5ms 补数） |
| 语音播报 | 复用音乐播放器：打断歌曲→播 `0:/prompt/*.wav`→自动回到原位置续播 |
| 网络 | ESP8266 USART2 AT + MQTT，WIFI 任务处理语音+云端 |
| 界面 | LVGL，应用界面含开关/滚轮/滑块控件 |
| RGB | WS2812 PB15 软件时序，语音可设颜色/七彩流动特效 |

任务栈：START 192 / LVGL 1024 / MUSIC 1536 / WIFI 1024 / MEAS 384（单位：字）
FreeRTOS 堆 60KB（CCM），任务创建后剩余约 1KB。

## 二、问题与解决过程

### P1.【已解决】系统偶发"整体死机"——WIFI 任务栈溢出

**现象**：指令突然全部没反应，疑似死机。
**定位**：`configCHECK_FOR_STACK_OVERFLOW=2`，溢出会触发钩子（全局关中断 + 死循环刷 `stack overflow`）。语音播报链路（`voice_handle → voice_say → mus_play_prompt → mus_wav_parse(512B 局部缓冲) → FatFs`）全部跑在 WIFI 任务里，原栈仅 3KB，余量不足。
**修复**：`STK_WIFI 768 → 1024 字(4KB)`；`FreeRTOSConfig.h` 打开 `INCLUDE_uxTaskGetStackHighWaterMark` 用于监测。实测心跳显示余量约 700 字，稳定。

### P2.【已移除】心跳诊断体系（排查期建设，交付前按需求关闭）

> 以下内容仅作排查历史保留：30s 心跳打印、WIFI/MUSIC 冻结监测、链路空闲 60s 提示
> 均已从代码中删除（串口只保留 `[voice] 收到命令` 和播报日志）。

`app_tasks.c` WIFI 任务每 30 秒输出一条心跳：

```
[wifi] 心跳 rx=76 cmds=19 last_cmd=0 秒前 mus=播放 WIFI栈余=708 字 MUSIC栈余=1470 字 beat=30488
```

| 字段 | 用途 |
|---|---|
| rx / cmds | 模块累计发送字节/命令帧数；不涨 = 模块侧没发数据 |
| last_cmd | 最后一条命令距今秒数 |
| mus | 音乐播放器状态（播放/暂停/停止），用于关联"聋"与音乐 |
| WIFI/MUSIC 栈余 | 高水位字数，低于 150 需警惕 |
| beat | MUSIC 任务心跳，两次心跳间不变 = 音乐任务卡死 |

配套监测：
- LVGL 任务检查 `g_wifi_beat`，冻结 >10 秒打印 `[watch] WIFI 任务已卡死...`（每 30s 重复）
- MUSIC 心跳 30s 无变化打印 `[watch] MUSIC 任务心跳 30 秒无变化...`
- rx 连续 60s 不涨打印 `[voice] 链路空闲超 60 秒...` 提示检查接线/重启模块

### P3.【根因已锁定，待用户验证】语音指令"突然没作用"

**排查历程**（多次日志佐证）：
1. 最初怀疑 WIFI 任务卡死 → 心跳证明任务活着
2. 怀疑模块死机 → 实测唤醒词（小盈小盈/小盈同学/小信小信）**始终有效**，只有命令词失效
3. 怀疑音乐震聋 → 出现过 `mus=停止`（没放歌）时连续 4 条指令 + 4 次播报后同样失效
4. **结论**：喇叭发出的任何声音（音乐、播报回复语）通过空气耦合进模块麦克风，把命令词识别引擎"灌聋"；唤醒引擎抗噪训练过所以一直活着。引擎几分钟后自行恢复，或喊一次唤醒词立即恢复。模块"自动退出"（发 0xAB，我们回"有需要再叫我"）时状态被复位，所以退出后又能用一阵

**佐证细节**：rx 只增不减、无乱码帧（不是接线/波特率问题）；MCU 侧栈余量、心跳全部正常。

**待验证**（用户尚未做）：连续下指令时用手指捂住模块麦克风孔——不聋即声学耦合实锤 → 棉花/纸巾贴麦克风孔即可解决；照样聋 → 模块固件缺陷，走"模块 VCC 加开关 + MCU 检测 rx 冻结自动断电重启"方案。

**已做的固件缓解**：
- ~~`MUS_VOL_LIMIT 60`：音乐音量硬上限~~（后期按需要已移除，音量恢复 0~100 全范围）
- `MUS_PROMPT_BOOST 55 → 40`：播报音量从 +17dB 降到 +12dB（55 时连续几条指令的播报就会灌聋识别）

### P4.【已解决】音乐音量/播报相关

- 音量平滑（每 10ms 走 1 级）必须放在常驻 MUSIC 任务，否则离开音乐界面后语音改音量硬件不动
- 唤醒/播报期间音乐自动暂停（`voice_hold` 机制）：唤醒 → 暂停 20s → 播报 → 到点续播，是绕开识别失灵的**可靠使用路径**

### P5.【已解决】播放日志语义混乱

- 播放日志区分为三种：`开始播放`（首次起播）/ `播报`（回复语）/ `恢复播放`（播报打断后回到原位置续播）
- 期间踩的坑：`start_pos` 经 `wavctrl.datastart` 归一化后恒 >0，用 `start_pos > 0` 判断"续播"永远为真 → 每次播放都误打"恢复播放"、播报还会连打两行。修复：归一化前先记录 `s_last_play_resumed`，并删除重复 printf

### P6.【已解决】应用界面不实时跟随语音

**现象**：语音改了风扇/灯/RGB，应用界面停在旧值（只在进界面时同步一次）。
**修复**：screen_app 增加 500ms 轮询定时器（`LV_EVENT_SCREEN_LOADED` 创建 / `SCREEN_UNLOADED` 销毁）：
- 开关类读硬件电平（LED 低有效）比对后刷新
- 风扇/舵机滚轮按 `fan_get_gear()` / `sg90_get_angle()` 同步
- RGB：特效（七彩流动）运行中**不覆盖控件**；用户正拖动的滑块不被抢（`lv_slider_is_dragged`）
- RGB 特效保护：程序化 `set_selected/set_value` 会触发 `VALUE_CHANGED`，误触"手动操作→停特效"逻辑；加 `s_rgb_entry_sync` 标志，进界面同步期间不停特效，同步结束（`screen_app_rgb_update()` 之后）清零

### P7.【已解决】回复语文件名错误

日志报 `打不开 0:/prompt/好的已为您设置.wav`：SD 卡上实际是"好的已为**你**设置.wav"。语音"温暖/音乐/睡眠模式"（0x33/0x34/0x35）改用正确文件名。

### P8.【说明】模块"自动退出"窗口短

- 退出超时（唤醒后无有效指令约 10s 左右退出）烧死在模块固件里，MCU 只接 RXD 改不了
- 智能音箱窗口长是云端 ASR 架构，离线命令词模块为抗误唤醒刻意做短
- 想改善：只有用厂商上位机（USB-TTL 连模块 TX）改配置——调窗口时长或**把常用指令设为免唤醒**（体验提升最大）
- MCU 侧已保证：唤醒回合内音乐暂停 20s，回合内识别成功率最高

## 四、遗留事项 / 下一步

1. **声学验证实验**（关键，几分钟）：连续下指令时手指捂模块麦克风孔，对比是否还聋 → 决定走"贴棉花/纸巾"还是"电源开关+自动重启"
2. **可选硬件方案**：模块 VCC 串 N-MOS/开关由 MCU GPIO 控制，固件检测 rx 冻结 90s 自动断电重启模块（代码已约定：用户定引脚后由固件实现）
3. **可选**：厂商上位机把常用指令词配置为免唤醒
4. 堆余量只剩约 1KB（60KB 总量），后续加功能需注意；`M0AR` 强制复位等播放器细节勿随意改动

## 五、日志速查

| 串口输出 | 含义 / 动作 |
|---|---|
| `[voice] 收到命令 0x..` | 识别到一条命令帧（4 字节/帧） |
| `[voice] 未知数据(n 字节): ..` | 收到不符合 `4F 00 xx F4` 的数据，打印原始字节 |
| `[music] 开始播放 / 播报 / 恢复播放` | 三种播放动作，一一对应 |
| `[voice] 最后一条指令已 30 秒，强制退出语音会话` | 30s 无新指令，MCU 侧结束会话、清接收残帧，并播报退出语（放歌时先打断后自动续播） |
| `stack overflow` 连刷 | 栈溢出死机（已通过扩容修复，不应再出现） |
